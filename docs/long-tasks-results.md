# Longer-task screen results

## Result

On 48 held-out checkable tasks of 4 to 32 steps, budget-forced plain Qwen3.5-4B completes
**38/48**. A BabyAGI-style loop run as host code around the same stock weights, which
writes its own ledger and decides after every step whether to stop, completes **20/48**,
and **25/48** when the host stops it at the true length. The primary comparison, loop
minus plain, is **−37.5 points** (item-bootstrap 95% CI [−52.1, −22.9]; 0 items improved,
18 regressed; exact McNemar p = 7.6e-6): the hypothesis that the loop does better is
contradicted. With the stop given, the loop is still −27.1 points behind ([−39.6, −14.6];
0 improved, 13 regressed), so the preregistered screen decision is **NO-GO**: this
adaptive loop is not worth compiling for capability.

The arms, caps, analysis, and decision rule were preregistered
([preregistration](long-tasks-preregistration.md)), and every task ran once per arm. The
records are in [`results/long-tasks-4b/`](../results/long-tasks-4b/).

## The screen

The compiled loop's fixed length is chosen when the checkpoint is built, so this screen
asks the question before compiling anything: on tasks longer and less specified than the
v3 suite, where one turn must carry every intermediate state in its own reasoning, does
the loop's structure (state re-read exactly each step, a 256-token reasoning span per
step, an explicit stop) beat plain chat at the same token budget?

- **Tasks.** The v4-horizon test split (`benchmarks/babyagi-v4-horizon.json`, SHA-256
  `ab3e35d7…`), generated by a seeded script and frozen before any model saw it: 16 long
  chains (every operation listed, v3's four families at 8, 16, 24, and 32 steps), 16
  rule-until tasks (one rule repeated until a stated condition holds, 4 to 28 steps, not
  stated), and 16 worklists (a job table whose jobs add follow-up jobs to a queue under a
  FIFO, LIFO, or alphabetical rule, 4 to 20 steps, not stated); 738 steps in all. A
  16-task development split was used only to check prompt wording. Scoring is the v3
  scorer: every intermediate state must match, and the result count must equal the true
  length L.
- **Loop (H-adapt).** The host advances the stages and holds the files. Qwen writes a
  ledger (an initial state and either a numbered task list or a rule and stop condition, at
  most 600 tokens); each cycle reads the latest result and the ledger, reasons for 256
  tokens, writes the new state (at most 240 tokens), and picks one of two tokens, continue
  or stop. Stopping, or cycle 40, ends the run. The prompt names each cycle's number but
  never L.
- **Loop stopped at L (H-oracle).** The same, with the host forcing continue before L and
  stop at L.
- **Plain (P-F2).** Thinking closed at 600 + 256 × L tokens, then an answer of at most
  241 × L tokens: the loop's maximum model-token allowance at L. The prompt states no
  length.

- **Stopping costs five tasks**, all rule-until. Qwen stopped exactly at L on 20 of the
  26 tasks whose steps were all correct when it decided (the preregistered bar for
  compiling was 90%); on those correct states its stop choices were right 344 times in
  350.
- **Execution costs most of the rest.** In 9 of the 11 worklist failures in each loop arm,
  the first wrong state has the right `done` list but drops a job that should have stayed
  queued (processing `fern` from `["iris", "fern"]`, the loop wrote `["birch", "reed"]`).
  Every execute step used all 256 of its reasoning tokens.
- **Plain fails ten tasks**: six exact-string long chains and four rule-until tasks of 10
  to 28 steps. It closed its own thinking on 5 of 48.
- **On the v3 suite the same loop (H-adapt-v3) completes 17/32**, against the compiled
  loop's 28/32 (−34.4 points, CI [−53.1, −18.8], 0 / 11) and budget-forced plain's 29/32.
  The loss is in the ledger: with a numbered task list, which the prompt asks for when the
  operations are listed, it completes 15 of 17; it wrote a rule instead for eight tasks and
  failed all eight, and seven ledgers did not parse.
- **Predictions that could fail held:** plain was force-closed on most tasks (43/48); the
  loop stopped at L completed at least as many tasks as Qwen's own stop (25 against 20);
  and plain's per-step exact rate fell faster with step index (87%, 79%, 66%, 74% by
  8-step band, against 59%, 57%, 74%, 71%), although only longer tasks reach later steps.

## What this means

With the [budget-forced results](plain-forced-v3-results.md), the evidence on Qwen3.5-4B
points one way: given an answer budget, plain Qwen is at least as good as the loop on short
chains and much better on these longer ones. The loop's value is control (an exact
controller, filesystem and HALT, and a trace that assigns every token to its owner), not
capability. This screen measures one adaptive design run as host code, not the compiled
checkpoint, whose length is fixed when it is built and was never run at these lengths; one
greedy run per task on one generated suite cannot detect small effects.

## Reproduction

`uv run python -m tests.test_long_tasks` checks every record's checksum, re-scores it
against its frozen task with `qfs.benchmark.score_item`, checks the plain arm's caps, and
recomputes every comparison above on CPU with `qfs.end_to_end._paired_summary`.
`results/long-tasks-4b/analysis.json` is the preregistered analysis run's output, and
[`results/long-tasks-4b/runner/`](../results/long-tasks-4b/runner/) is the source that
produced the records, as run; it imports the research lab's own packages, so it does not
run from this repository.
