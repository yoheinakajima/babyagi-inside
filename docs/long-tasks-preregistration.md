# E15 preregistration: Host screen: does an adaptive-length loop beat plain chat on long and open-ended tasks?

Written on 2026-11-07 before any E15 run, then locked with `uv run lab prereg E15`. After
the lock, `lab run` refuses to start if this file or `config.yaml` changes. Any later
change is a dated amendment (`uv run lab prereg E15 --amend "reason"`) described under
Deviations. Environment: m5. Depends on: E12, E14. Design:
`experiments/drafts/E15-unbounded-design.md` (sections 2-4); implementation note:
`notes.md`.

## Question

With stock Qwen3.5-4B and no compiled checkpoint, does a host-simulated BabyAGI-style
ledger loop that decides for itself when to stop complete more of 48 held-out long and
open-ended chains than plain chat at a matched token budget? The loop writes one ledger,
then repeats read state, read ledger, execute and decide, where Qwen picks CONTINUE or DONE
as one of two tokens after every execute, with a hard cap of 40 cycles. Plain chat is
budget-forced as in E14 F2. The answer decides whether this adaptive loop (design M3, M2
and M4a) is worth compiling.

## Why

On v3 (lengths 2-8, every operation listed), the loop's schedule is not what limits Qwen:
E12's compiled 4B loop completed 28/32 chains and its host simulation 27/32, and E14's
budget-forced plain 4B (F2) completed 29/32. The two arms fail on the same per-operation
slips. What the loop has and one forced turn lacks matters, if at all, only at longer
horizons and when the length is not given: each step re-reads its state token-exactly,
the step pointer cannot skip or merge a step, each step gets a fixed 256-token reasoning
allowance (plain 4B hit its thinking cap on every E14 F2 run), and each step ends with an
explicit stop decision. The design draft judges this a weak case: worth a host screen of
about a day of M5 decoding, not a compile. A null result means the loop's value has to be
argued from exactness and inspectability, never from accuracy.

## Hypothesis

H-adapt: H-adapt completes more test chains than P-F2: the paired difference (H-adapt
minus P-F2) has an item-bootstrap 95% CI lower bound above zero.

No other directional hypothesis is tested. Predictions that can fail, reported as they
fall: P-F2 is force-closed on most test items (as on 32/32 E14 F2 runs); H-oracle completes
at least as many chains as H-adapt (Qwen's stop choices can only cost chains on items it
executes exactly); and P-F2's per-step exact rate falls faster with step index than
H-oracle's.

## Acceptance criteria

Fixed before any run. Each is pass/fail.

1. Completeness: every test item has a record under H-adapt, H-oracle and P-F2, and every
   v3 item under H-adapt-v3, each with an identity matching this protocol (arm, split,
   item, suite SHA-256, ROM SHA-256, settings, caps), and one runner version per arm.
2. Feasibility: the H-adapt test traces pass the audit (Metrics), or every failure is of a
   kind with a preregistered fix (Analysis plan).
3. H-adapt: the H-adapt minus P-F2 comparison is SUPPORTED by the CI rule in the Analysis
   plan.
4. Stopping: H-adapt stops exactly at L on at least 90% of the stop-eligible test items.
5. Decision: the screen decision (GO, REDIRECT, NO-GO or INCONCLUSIVE) is computed by the
   rule in the Analysis plan and recorded with the analysis run's run_id. H-adapt-v3 is
   reported, not tested.

## Arms

Held fixed in every arm: stock Qwen3.5-4B (`models/Qwen3.5-4B`, SHA-256 pinned in
config.yaml), bf16 on MPS, greedy, one run per item. Scoring is `qfs.benchmark.score_item`
(`exact_state_chain`, which fails any result count other than L). There is no retry or
verify arm. L is the item's gold length (`cycles`).

**The loop** (H-adapt, H-oracle, H-adapt-v3) is a host simulation built from
`qfs.agent_native`'s `NativeRunner`, `stage_view`, `visible_response_tokens` and
`choose_token` (through `NativeRunner.pick`). `run_native` walks a static list, so
`harness.adaptive_screen.run_loop` owns the loop. The objective is prefilled with the
qwenFS tool schema, as in `run_native`. Before every stage the host feeds 0.25 times the
newline embedding, the control-token surrogate of E9. The stages are:

| Stage | Forced tokens | Qwen | Then |
| --- | --- | --- | --- |
| create | 279 (ROM, opening `{`) | the ledger: `initial`, `tasks`, `rule`, `until`; at most 600 payload tokens, to `</tool_call>` | cycle 1 |
| read result.json | 25 + response | none | not found at cycle 1 |
| read ledger.json | 25 + response | none | |
| execute | 173 ROM, 32 suffix opening `{"result":` | 256 reasoning tokens (control tokens masked), then at most 240 payload tokens, to `</tool_call>` | |
| decide | 116 ROM (101 at the lock; see Deviations) | one token, restricted to `1` (CONTINUE) or `2` (DONE); no tool call | DONE, or the end of cycle 40, halts |

The host holds files in a dictionary. A write that does not close its call stops the run.
The results are the `result` values of the execute writes, one per cycle and aligned by
cycle (an unparsable write is a wrong answer at its own step). The ROM, identical for all
three categories, is in `harness/adaptive_screen.py`, and its SHA-256 is config.yaml's
`rom_sha256`. It states each cycle's own number as two digit tokens at fixed offsets (as a
compiled counter would render it) and never L. Category A fills `tasks`, and step c runs
task c. Categories B and C fill `rule` and `until`, and each step applies the rule once.
The worklist queue lives in the result state (M4a), and its job table goes into `rule`.

| Arm | Suite | Decide stage |
| --- | --- | --- |
| **H-adapt (primary)** | v4 test | Qwen's choice among `1` and `2` (greedy over the two logits) |
| H-oracle | v4 test | host-forced: `1` before cycle L, `2` at L (a fixed-length loop); Qwen's own pick is recorded |
| **P-F2** | v4 test | plain chat (below) |
| H-adapt-v3 | v3 | as H-adapt |

**P-F2** is `harness.plain_forced.generate_forced`: thinking until `</think>` or a cap of
600 + 256 x L new tokens, where the host appends `"\n</think>\n\n"`, then an answer of at
most 241 x L tokens. Together these equal the loop's maximum model-token allowance at the
gold length (a 600-token ledger write, and per step 256 reasoning tokens, a 240-token
result write and a one-token decision), split as the loop splits it. The prompt is E14's plain prompt (`plain_forced.plain_prompt`) with
its clause "has exactly N entries in task order" replaced by "has one entry per
operation, in task order". The prompt states no length. The parse takes the last JSON
object with a `results` list in the whole generation, of any length (`parse_open`).
E14's `parse_plain`, which picks an array of exactly L entries, is recorded only as a
diagnostic.

Maximum model tokens at a stop exactly at L: the loop 497L + 600 (L x 256 reasoning,
L x 240 result writes, a 600-token ledger, L choices), and P-F2 512L + 256. The loop's
maximum is the larger one only for L <= 22, by at most 284 tokens, and only through the
ledger cap: the reference ledgers need at most 261 tokens. A loop that runs past L uses
more tokens, but such a chain fails. Forced tokens (ROM and simulated qwenFS responses)
are not model tokens, as in E14 F2.

## Metrics

Primary: adapt_minus_plain_delta: exact chains over the 48 test items, H-adapt minus P-F2,
paired, with the item-bootstrap 95% CI (10,000 resamples, seed 0) and exact McNemar p from
`qfs.end_to_end._paired_summary`.

Secondary, from the same statistics: H-oracle minus P-F2, and H-adapt minus H-oracle. Per
arm:
- chains and exact steps, by horizon category, by v3 domain, and by length bucket (<= 8,
  9-16, 17-24, 25-32);
- stop outcome: for the loops, exact, early, late (DONE after L, or a failed write after
  CONTINUE at L), cap (no DONE within 40 cycles) or aborted (a failed write at or before
  L); for P-F2, the result count, exact, early, late or unparsed;
- the exact-step rate and prefix survival by step index;
- first failed step and failure kind (wrong value, missing step, extra steps);
- the native logit margin, logit(`1`) minus logit(`2`), at each decision, summarized on
  stop-eligible items at CONTINUE-due and DONE-due cycles, with how often Qwen's own pick
  (also under H-oracle) is the correct one;
- the ledger shape Qwen wrote, by category;
- model, forced and context tokens, and seconds;
- for P-F2, runs that closed their own thinking, were force-closed or reached the answer
  cap, and the parse rate over the whole generation, over the answer alone, and with E14's
  gold-length parser.

H-adapt-v3: chains, with descriptive paired differences against E12's compiled 4B loop
(`provenance/e14-compiled.json`), E9's host 4B arm (`provenance/e12-frozen-comparisons.json`)
and, when its 32 records are present, E14 F2-4b.

Stop-eligible item: one on which every step before the gold stop was exact, so Qwen made
its stop decision on a correct state. That means steps 1..k for an early DONE at cycle k,
and steps 1..L otherwise. Aborted runs are not eligible.

Feasibility audit, on every loop trace. The host does not enforce these qwenFS and
controller limits:
- violations: more than 62 writes to one file, more than 32 files, a stored text over 600
  tokens, a stage span over 600, more than 40 cycles;
- flags, reported but not failures: a stored text over 500 tokens, a payload write that
  reached its limit.

The thresholds of criteria 2-4 are given there and in the Analysis plan.

## Seeds and decoding

Greedy (temperature 0, `do_sample=False`). `NativeRunner`'s generator is seeded 0 but
unused at temperature 0. One run per item per arm. bf16, MPS. Loop: 256 reasoning tokens
per execute, at most 240 payload tokens per result write and 600 for the ledger write,
cap 40 cycles, control surrogate 0.25, typed choice over token ids 16 (`1`) and 17 (`2`).
P-F2: thinking cap 600 + 256 x L, answer cap 241 x L, close tokens 198, 248069, 271.

## Stop conditions

- Each item runs once per arm. An interrupted step resumes: records whose identity matches
  are kept, and the rest run. Each attempt is logged. A record is never edited or dropped.
  If a step cannot finish within its cap, the missing items are reported and the decision
  is INCONCLUSIVE.
- Each test step refuses to decode, and logs itself invalid, if the harness's ROM SHA-256
  differs from config.yaml's `rom_sha256` or the static check fails (choice tokens, fixed
  digit offsets, spans of at most 600).
- dev-check: before the first test step, runs on the dev split only (H-adapt, H-oracle
  or P-F2: `run ARM dev`, optionally `--only ITEM`). At most three wording revisions are allowed, and between them only the strings
  CREATE, EXECUTE, DECIDE and PLAIN_SUFFIX in `harness/adaptive_screen.py` may change. Arms,
  caps, limits, scoring, audit and decision rule do not change. If the final wording
  differs from the locked digest, it is recorded by amendment (a new `rom_sha256`, and a
  Deviations entry) before any test step. Dev results are reported as dev results and
  never pooled with test.
- An out-of-memory error or a crash is a failed run, logged with its error text, and the
  step resumes from its records.

## Analysis plan

Each paired difference is read by its CI, as in E12 and E14: SUPPORTED when the lower bound
is above zero, CONTRADICTED when the upper bound is below zero, otherwise INCONCLUSIVE
(`harness.port.verdict`). McNemar p is reported and takes no part in any decision. The
decision rule follows design section 4 and is applied in this order:

1. **GO (compile v1)** when all of these hold: the H-adapt minus P-F2 CI lower bound is
   above 0 (criterion 3); the audit passes (criterion 2); and H-adapt's exact-stop rate on
   stop-eligible items is at least 0.90 (criterion 4).
2. **REDIRECT** when GO fails but the H-oracle minus P-F2 CI lower bound is above 0. The
   loop helps but Qwen's stop decisions do not. Screen the model-free stop (M1b/M4b) next
   and compile nothing.
3. **NO-GO** when the H-oracle minus P-F2 CI upper bound is below 0, or both point
   estimates (H-adapt and H-oracle, each minus P-F2) are at most 0. No compile for
   capability; report it as a negative result.
4. **INCONCLUSIVE** otherwise, or when criterion 1 fails. No compile.

The audit passes when no H-adapt test trace has a violation, or when every violation is of
a kind with a preregistered fix. Only one kind has one: more than 62 writes to one file,
fixed by rotating result files (E2's rotation item). It cannot occur with a 40-cycle cap.
Every other violation fails criterion 2. With no stop-eligible item, criterion 4 fails.

The decision is computed by `python -m harness.adaptive_screen analyze`
(`decision_rule`). The secondary comparisons, categories, buckets and H-adapt-v3 are
descriptive. Reporting commitment: the decision and the primary difference are reported
whatever they are, including in the design draft's follow-up and in any later
compile proposal. A host screen is not evidence about a compiled checkpoint: the host
advances phases and holds files.
